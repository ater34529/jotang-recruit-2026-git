# 一、 HTTP 请求 & 响应
## 1.标准HTTP请求的组成
### ‌请求行‌：位于请求第一行，格式为「请求方法 资源URI HTTP协议版本」，  
例如 GET /index.html HTTP/1.1，明确告知服务器要执行的操作和目标资源。

### ‌请求头‌：以键值对形式传递客户端的附加信息，   
比如Host（目标服务器域名，HTTP/1.1强制要求）、User-Agent（客户端浏览器标识）、Cookie（会话状态信息）、Content-Type（请求体的数据格式）等。

### ‌空行‌：仅包含回车换行的特殊行，是HTTP协议的固定分隔符，用于标记请求头已经全部结束，后面的内容就是请求体。

### ‌请求体（可选）‌：用于传输客户端提交给服务器的实际数据，常见于POST、PUT等方法，  
比如表单内容、上传的文件、JSON数据；GET请求的请求体通常为空，数据会放在URL的查询字符串中。
## 2.标准HTTP响应的组成
‌### 状态行‌：位于响应第一行，格式为「HTTP协议版本 状态码 状态描述」，  
例如 HTTP/1.1 200 OK，直接告知客户端本次请求的处理结果。

### 响应头‌：以键值对形式传递服务器的附加信息，  
比如Content-Type（响应体的数据格式，如text/html）、Content-Length（响应体长度）、Server（服务器软件信息）、Set-Cookie（向客户端写入会话Cookie）等。

### ‌空行‌：和请求中的空行作用完全一致，用于分隔响应头和响应体，标记响应头结束。

### 响应体（可选）‌：服务器返回给客户端的实际资源内容，  
比如HTML网页、图片、JSON接口数据、文件内容等，是客户端最终要获取的核心数据。
## 2.GET 和 POST
### GET
当在浏览器地址栏输入https://search.example.com/books?keyword=python&page=2&size=20  
按下回车的瞬间，浏览器就组装好了一个标准的GET请求发向服务器。  
请求行明确标注GET /books?keyword=python&page=2&size=20 HTTP/1.1，所有查询参数直接拼在URL末尾，没有额外的请求体。  
请求头里带上浏览器标识、可接受的响应格式，服务器收到后不会修改任何数据库数据，只根据URL里的关键词、页码参数从图书库中筛选出对应结果返回，整个过程完全只读，重复刷新多少次都不会产生副作用，浏览器还会自动把这个结果缓存下来，下次再搜相同关键词时直接从本地取数据，页面加载速度能快好几倍。
### POST
当你在网站的注册页面填完手机号、密码、昵称，点击“提交注册”按钮时，浏览器就会发起一个POST请求。请求行是POST /api/user/register HTTP/1.1，所有用户填写的注册数据不会出现在URL里，而是完整封装在HTTP请求体中，同时请求头里会带上Content-Type: application/json告诉服务器要解析JSON格式的数据。  
服务器收到请求后不会直接返回静态资源，而是校验手机号是否已注册、密码强度是否合规，校验通过后在数据库里新增一条用户记录，返回注册成功的响应。   
这个操作是非幂等的，重复点击提交按钮就可能生成多个重复账号，浏览器默认不会缓存这个请求，也不会把密码这类敏感参数留在历史记录里，从根源上避免了GET请求把敏感信息暴露在地址栏的安全隐患。
## 3.状态码
‌HTTP状态码是服务器返回的三位数字代码‌，用于向客户端传递当前请求的处理结果，明确告知请求是成功、需要重定向还是出现了错误，是Web通信中标准化的“结果反馈语言”。

五大类常见状态码
### 1. 1xx 信息类
表示服务器已收到请求，正在处理中，需要客户端继续后续操作：

‌100 Continue‌：客户端可继续发送剩余请求内容，常用于大文件上传前的试探校验
‌101 Switching Protocols‌：同意切换协议，典型场景是HTTP升级为WebSocket连接
### 2. 2xx 成功类
表示请求已被服务器成功接收、理解并处理完成：

‌200 OK‌：最通用的成功码，网页正常加载、接口返回数据时几乎都会返回该状态
‌201 Created‌：资源创建成功，比如新增用户、提交笔记后返回，响应头会附带新资源的地址
‌204 No Content‌：操作成功但无返回内容，常用于删除接口，避免页面发生不必要的跳转
‌206 Partial Content‌：返回部分内容，用于视频分段加载、断点续传场景
### 3. 3xx 重定向类
表示需要客户端进一步发起请求，才能完成当前操作：

‌301 Moved Permanently‌：永久重定向，旧网址永久迁移到新地址，搜索引擎会自动转移原网址的权重
‌302 Found‌：临时重定向，资源暂时位于其他地址，常见于未登录时自动跳转到登录页
‌304 Not Modified‌：资源未修改，客户端可直接使用本地缓存，大幅节省带宽
‌307 Temporary Redirect‌：严格的临时重定向，会保留原请求的方法（比如POST请求重定向后仍保持POST方法）
### 4. 4xx 客户端错误类
表示请求存在问题，责任方在客户端：

‌400 Bad Request‌：请求格式错误，比如JSON解析失败、必填参数缺失
‌401 Unauthorized‌：未完成身份认证，需要用户登录后才能访问
‌403 Forbidden‌：服务器拒绝访问，即使已登录也没有对应资源的操作权限
‌404 Not Found‌：请求的资源不存在，通常是网址输入错误或页面已被删除
‌405 Method Not Allowed‌：请求方法不被允许，比如接口只支持POST，却用GET方式调用
‌429 Too Many Requests‌：请求过于频繁，触发了服务器的限流规则
### 5. 5xx 服务器错误类
表示服务器处理合法请求时出现了内部故障：

‌500 Internal Server Error‌：通用服务器错误，通常是后端代码Bug、数据库连接失败导致
‌502 Bad Gateway‌：网关错误，反向代理服务器无法连接到后端的业务服务
‌503 Service Unavailable‌：服务暂时不可用，常见于服务器过载、正在停机维护
‌504 Gateway Timeout‌：网关超时，后端服务处理请求的时间过长，没有及时返回响应

# 三、 JSON
## 1. JSON 数据长什么样？
JSON 主要由两种结构组成：‌对象‌（键值对集合）和 ‌数组‌（有序列表）。

基本语法规则  
‌对象‌：使用花括号 {} 包裹，内部是 key: value 对。  
‌Key‌ 必须是字符串，且必须用‌双引号‌ "" 包裹。  
‌Value‌ 可以是字符串、数字、布尔值、null、对象或数组。  
键值对之间用逗号 , 分隔。

‌数组‌：使用方括号 [] 包裹，内部是一系列值。
值之间用逗号 , 分隔。

‌数据类型‌：
字符串："Hello"
数字：42, 3.14
布尔值：true, false （全小写）
空值：null
对象：{"name": "Alice"}
数组：[1, 2, 3]
## 2.如何使用你所选择的编程语言来将对象转化成 JSON, 或者将 JSON 转化成一个对象?
### 第一步：准备“工具” (依赖)
Java 原生不带 JSON 处理功能，需要引入 Jackson 库。

‌动作‌：在 pom.xml 中加入 jackson-databind 依赖。  
‌核心类‌：ObjectMapper。
### 第二步：准备“数据模型” (Java Bean)
JSON 转换必须基于一个标准的 Java 类。

‌动作‌：创建一个类（如 User）。

‌硬性要求‌：  
必须有无参构造函数‌（public User() {}）。  
字段必须是private‌。  
必须提供 public 的 ‌Getter 和 Setter‌ 方法（或者使用 Lombok 的 @Data）。
### 第三步：掌握“两个方向”的核心代码。
#### 方向 1：对象 -> JSON (序列化/打包)
当你想把 Java 对象发给前端或存到数据库时。

‌方法‌：mapper.writeValueAsString(对象)  
‌结果‌：得到一个 String 类型的 JSON 字符串。
```java
ObjectMapper mapper = new ObjectMapper();
User user = new User("张三", 25);
String json = mapper.writeValueAsString(user); 
// 结果: {"name":"张三","age":25}
```
#### 方向 2：JSON -> 对象 (反序列化/拆包)
当你收到前端传来的 JSON 字符串，想变成 Java 对象方便操作时。

‌方法‌：mapper.readValue(JSON字符串, 目标类.class)  
‌结果‌：得到一个填充好数据的 Java 对象。
```java
String jsonInput = "{\"name\":\"李四\",\"age\":30}";
User user = mapper.readValue(jsonInput, User.class);
System.out.println(user.getName()); // 输出: 李四
```
# 四、 HTTPS
HTTPS 的加密过程核心是通过 ‌SSL/TLS 协议‌ 结合对称加密、非对称加密与数字证书，完成身份验证、安全密钥协商和后续加密通信，全程保障数据传输的保密性、完整性和身份真实性。

## 1. 前置基础：两类加密的分工
HTTPS 没有单独依赖某一种加密方式，而是结合两者优势解决效率与安全问题：

‌对称加密‌：加密解密使用同一密钥，速度极快，适合大量数据传输，但密钥本身的安全分发是难题 。  
‌非对称加密‌：通过公钥+私钥的密钥对实现，公钥可公开分发，私钥必须严格保密；公钥加密的数据只有对应私钥能解密，反之亦然，专门用来安全传递对称加密的密钥 。
## 2. 完整加密流程（TLS 握手阶段）
### 第一步：建立基础连接与能力协商
客户端（浏览器）先和服务器通过 TCP 三次握手建立可靠连接，随后立即发送 Client Hello 报文，携带支持的 TLS 版本、加密算法套件、客户端随机数等信息。  
服务器返回 Server Hello，选定双方都支持的最高安全版本和加密算法，同时生成服务器随机数返回给客户端 。

### 第二步：身份验证与证书校验
服务器向客户端发送由权威 CA 机构签发的数字证书，证书内包含服务器域名、公钥、CA 数字签名、有效期等信息。  
客户端收到证书后完成严格校验：检查证书是否在有效期内、域名是否匹配、是否由系统信任的 CA 根证书签名、是否被吊销。校验不通过时浏览器会直接弹出「连接不安全」的警告，终止通信 。

### 第三步：安全协商会话密钥
证书验证通过后，客户端生成预主密钥（Pre-Master Secret），用服务器证书中的公钥加密后发送给服务器；服务器用自己的私钥解密得到预主密钥。  
双方结合之前交换的客户端随机数、服务器随机数，通过相同的加密算法独立计算出完全一致的‌会话密钥‌。这个会话密钥全程不会在网络中明文传输，第三方无法截获 。

### 第四步：握手确认与加密通信启动
客户端和服务器分别生成包含所有握手消息摘要的 Finished 报文发送给对方，验证通过后握手正式完成。  
后续所有 HTTP 数据都通过这个会话密钥，使用 AES-128-GCM、ChaCha20-Poly1305 等高性能对称加密算法加密传输，同时附带消息认证码（MAC），防止数据被篡改 。
